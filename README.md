# 장애 대응형 비동기 파일 처리 플랫폼

## 1. 프로젝트 개요

대규모 파일 처리 서비스를 가정합니다.

사용자가 파일을 업로드하면 **썸네일 생성, 포맷 변환, 데이터 분석** 등의 작업이 발생하며, 각 작업은 비동기로 처리됩니다.

파일 처리 작업은 종류에 따라 처리 시간과 필요한 CPU·메모리가 다르며, 특정 시점에는 특정 유형의 작업에 요청이 집중될 수 있습니다.

따라서 작업 유형별 Worker를 독립적으로 운영하고, **작업량 변화에 따라 처리 자원을 확장할 수 있으며 일부 Worker에 장애가 발생하더라도 전체 작업 처리가 중단되지 않는 시스템**을 설계하는 것을 목표로 합니다.

<br>

## 2. 서비스 시나리오

파일이 업로드되면 API는 파일을 직접 처리하지 않고 처리해야 할 작업을 Queue에 등록합니다.

Queue에 등록된 작업은 작업 유형에 맞는 Worker가 가져가 비동기로 처리합니다.

```text
                     Client
                       │
                       ▼
                  Upload API
                       │
                       ▼
                     Queue
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      Thumbnail     Converter     Analyzer
       Worker        Worker        Worker
          │            │            │
          └────────────┼────────────┘
                       ▼
                 Object Storage
```

각 Worker는 서로 다른 처리 특성을 가진다고 가정합니다.

| Worker | 역할 | 처리 특성 |
| --- | --- | --- |
| Thumbnail Worker | 이미지 썸네일 생성 | 처리 시간이 짧고 요청량이 많음 |
| Converter Worker | 파일 포맷 변환 | CPU 사용량이 높고 처리 시간이 김 |
| Analyzer Worker | 파일 데이터 분석 | 작업별 처리 시간이 길고 변동성이 큼 |

특정 작업에 요청이 집중될 수도 있습니다.

예를 들어 Converter 작업량만 급격하게 증가한 경우 Thumbnail과 Analyzer의 작업량은 그대로인 반면, Converter Worker에는 많은 작업이 대기하게 됩니다.

따라서 모든 Worker를 동일하게 확장하는 것이 아니라 **각 Workload의 상황에 따라 필요한 Worker를 독립적으로 확장할 수 있어야 합니다.**

<br>

## 3. 시스템 가정

### Traffic

평상시에는 Queue에 초당 **10~50개의 작업**이 유입되며, 특정 이벤트나 대량 업로드가 발생하면 순간적으로 최대 **1,000 jobs/sec**까지 증가할 수 있다고 가정합니다.

### Workload

각 작업 유형은 서로 다른 처리 시간과 자원 사용량을 가지며, 특정 Workload만 독립적으로 급증할 수 있습니다.

### Failure

Worker는 처리 도중 예기치 않게 종료될 수 있으며, 단일 Worker 장애가 전체 작업 처리 중단으로 이어져서는 안 됩니다.

처리 중 실패한 작업은 유실되지 않아야 하며, 일시적인 실패와 반복적인 실패를 구분하여 처리할 수 있어야 합니다.

### Scaling

작업량이 증가하면 처리 가능한 Worker 수를 늘리고, 작업량이 감소하면 불필요한 Worker를 줄일 수 있어야 합니다.

특정 Workload가 증가한 경우 해당 Worker만 독립적으로 확장할 수 있어야 합니다.

### Deployment

서비스가 운영 중인 상황에서도 새로운 버전을 배포할 수 있어야 하며, 배포 과정이 기존 작업 처리에 미치는 영향을 최소화해야 합니다.
